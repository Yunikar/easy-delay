# Easy Delay — decisions

Each entry: decision, then why. Open questions are listed separately at the end.

## 1. zero PDC 是核心诉求

**结论**：插件对宿主报告 0 采样延迟，不做插件延迟补偿（PDC）；音轨在 DAW 时间轴上保持原位，只是听到的声音晚了一个延迟量。

**理由**：用户明确要“设定延迟时长，同时不影响 DAW 的延迟”。如果按常规报真实延迟，宿主会整轨前移去补偿，听到的相对位置不会变，需求就落空了。

## 2. 起播行为：先干声占位，缓冲区满后切到延迟声

**结论**：插件启动/重置后，内部延迟线还没填满请求的延迟深度时，输出干声；填满后平滑切到延迟声。不静音、不丢开头。

**理由**：插件报 0 延迟，宿主不会提前喂数据，所以第一个延迟时长内没有可读的历史数据。完全静音会让开头“消失”；干声占位是听感上最不突兀的做法。切换用 mix 平滑（约 20 ms），避免 click。

**副作用**：给长延迟（如 2 s）从曲首第一拍开始时，头 2 s 听到的是原声，2 s 后才进入延迟声。这是该架构的固有行为，不是 bug。

## 3. 播放中改延迟时间：磁带式滑音

**结论**：延迟时间参数用一阶平滑（时间常数约 60 ms）送进读数头，读头连续滑动产生 pitch glide，不跳变、不 click。

**理由**：用户选择“磁带式滑音”。连续的读头运动天然避免跳变爆音；代价是大幅拖动时会听到明显的变调。

## 4. 参数范围

**结论**：Delay 0–2000 ms（默认 250 ms，带 0.45 skew），Feedback 0–100%（默认 25%），Mix 0–100%（默认 35%）。

**理由**：用户确认 0–2000 ms + 干湿比 + 反馈。反馈写入路径乘 0.5 并硬限幅，保证 100% 反馈时是衰减而不是自激爆炸。

## 5. 不做 BPM 同步、不做多抽头

**结论**：只做毫秒延迟、反馈、干湿比、重置。

**理由**：用户没有要求音符时值同步或其它效果；控制范围，先把核心行为做稳。

## 6. 平台与构建

**结论**：Windows x64 VST3，JUCE 9（vendored 在 third_party/），CMake + MSVC 2022 构建；不改用户现有环境变量，CMake 用随工程下载的便携版。

**理由**：用户环境是 Windows + Studio One，机器上有 VS 2022 的 C++ 工具链，但没有 CMake；把 CMake 和 JUCE 放进工程，构建可复现且离线。

## 7. 安装方式

**结论**：交付 zip + 自提权安装脚本（`install.cmd` → `install.ps1`），装到系统级 VST3 目录 `C:\Program Files\Common Files\VST3\EasyDelay.vst3`，并在 Windows“应用和功能”里注册卸载项，卸载时连同插件目录和注册表项一起删除。

**理由**：用户选择系统级目录，Studio One 默认扫描该路径；写 Program Files 必须提权，所以安装脚本自己请求 UAC，而不是要求用户手动复制。

**为什么不是 Inno Setup**：本会话的沙箱禁止写 Program Files，也禁止安装需要提权的工具；生成的 Inno 安装包无法在这里构建/自测。用脚本方案可以在这里验证语法与流程，且不需要额外工具链。

## 8. 界面

**结论**：单页、默认 520×280、深灰底 + 单一琥珀色强调；只有 Delay/Feedback/Mix 三个旋钮、实时读数、状态字（DELAYED / DRY - BUFFERING）和 Reset。

**理由**：见 `DESIGN.md`。插件面板不是网页，不做卡片、渐变、图标堆砌；状态字直接说明当前是不是在干声占位期。

## 9. 开源

**结论**：以 AGPLv3 公开在 GitHub（`Yunikar/easy-delay`）；`third_party/` 不进仓库，构建前跑 `tools/fetch-deps.ps1` 拉 JUCE 和 CMake。

**理由**：JUCE 免费使用必须遵守 AGPLv3，所以仓库整体用 AGPLv3 是唯一免费且合规的选择。依赖不入库是为了仓库轻量；脚本固定版本，构建可复现。CI 用同一个脚本，保证“干净的克隆能构建”这件事被持续验证。
